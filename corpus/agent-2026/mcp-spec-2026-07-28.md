# MCP 2026-07-28 规范 — 从「工具协议」到「agent 运行时协议」

- 分类：agent-2026 / 协议与工具联邦
- 来源：Model Context Protocol（Anthropic 发起，社区维护）
- 核验日期：2026-10-25；核验状态：verified（webfetch 200，正文命中）

## 来源
- https://modelcontextprotocol.io/specification/2026-07-28

## 核验（实际读到的）
- 版本页明确为 **2026-07-28**；JSON-RPC 2.0；**stateless, self-contained requests**；**per-request capability negotiation**。
- 服务端三原语：Resources（上下文/数据）、Prompts（模板化消息/工作流）、Tools（可执行函数）；客户端原语：**Elicitation**（服务端反向请求用户输入）。
- 扩展为 opt-in、初始化时协商：**Tasks**（长任务异步执行、轮询、飞行中输入、durable handles）、**Skills over MCP**（结构化技能包）、**MCP Apps**（会话内交互 UI）。
- 安全章节点名三条原则：显式用户同意、数据最小外发、**工具描述/注解默认不可信（除非来自可信服务端）**。

## 架构要素
- 拓扑：Host（LLM 应用）→ Client（连接器）→ Server（上下文与能力提供方），像 LSP 之于编辑器。
- 状态模型：核心协议**无状态**，长任务状态外移到 Tasks 扩展的 durable handle。
- 能力发现：`server/discover` 返回能力与工具清单；扩展在 per-request capabilities 里声明。
- 信任边界：工具=任意代码执行；描述文本不可信；同意与授权由 Host 实现而非协议强制。

## 对我们的启示
- 我们已实现 2026-07-28 版本号与 `server/discover`（`inkblade/mcp_server.py:36`、`:523`），但**只用到 Tools 一个原语**：没有 Resources/Prompts、没有 Elicitation、没有 Tasks。
- 我们的「审批」本质是 Elicitation + Tasks 的 `input_required`，却用进程内队列 `explorer/queue.json` 自造（`inkblade/core/explorer.py:35`）——可直接对齐协议语义，获得跨客户端互操作。
- 「工具描述不可信」直接对应我们的 LLM 降级策略（`explorer.py:176-177`）：外部 MCP 工具接入后，描述投毒是 ASI04/ASI02 的入口，必须在工具注册时做来源与摘要校验。
